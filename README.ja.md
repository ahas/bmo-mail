# bmo-mail

独自の API を持つ 1 つのサービスとしてのメールです。ログインアカウントごとに自分のメールボックスを持ち、
メールボックスは画面から追加し、アカウントの種類ごとのアダプターを通じて読み、書き、監視します。最初の
アダプターは IMAP とサブミッションです。一覧のスレッド化とページングを自前で行い、メールの到着時にフィルター
ルールを実行し、差出人のロゴを探し、送信したメッセージをアカウントの取り消し期間のあいだ保留して取り消せる
ようにし、何が届き何が変わったかを独自のイベントストリームで知らせます。他のサービスは呼び出しません。
ホスト型ツール `bmo/mail_sent` は、ある人がある日に送ったメールを、その人の PC 上の Outlook から、または任意の
ページトークンサービスが貸すトークンで Microsoft Graph から読み取ります。その際、エージェンシー、レシーバー、
アカウントサービス、ノードサービス、そしてそのページトークンサービスを経由します。コーディングハーネスは MCP サーバー `bmo-mail mcp` と `bmo-mail`
スキルを通じてこのサービスを取り込み、コンソールは `docs/api.md` が定めるとおり、サービスがマニフェストと
ともに提供する `client/` のバンドルを通じて画面を取り込みます。

## テスト

テストベッドの `personal-data` チェックが個人データのルール(`PERSONAL-DATA.md`)を守ります。リポジトリには
次のテストがあります。旧アーカイブのインポートは `tests/import.rs`、アカウントは `tests/accounts.rs` で、
アカウントのルート、あるオーナーキーが他のオーナーのものに届かないこと、秘密情報の封印、アカウントファイルの
インポートを扱います。切断された接続上のウォッチャーは `tests/watcher.rs`、POP3 アカウントは
`tests/pop3.rs` で、テスト用の POP3 サーバーと送信サーバーを相手に、受信トレイの一覧、添付ファイル付きメールの
読み取り、`UIDL` による新着メールの判別、ストアに下書きとして保存した返信の送信を扱います。メールサーバーは `tests/servers.rs` で、サーバーが記録になる前のアカウントを
同じ設定ごとに一つのサーバー記録へ移すこと、テスト用アカウントサービスの委任チェーンでオーナーが届くサーバー、
その中から選ぶアカウント、テスト用送信サーバーを相手にしたアカウントサービスのシステムメール送信を扱います。コンソールの面は
`tests/console.rs` で、ベンダリングした bmo-ui リリース自身の読み取りで読んだ提供マニフェストと、コンソールの
認証情報とサービスのトークンがどこまで届くかを扱います。画面の文言は `tests/words.rs` で、画面が書くすべての
キーが自身の言語パックのもの、またはリリースの `wording-keys` モジュールが挙げるものであることを確かめます。
ホスト型ツールは `tests/sent_mail.rs` で、ツールホストが呼び出すのと同じ方法で、エージェンシー、ノード
サービス、ページトークンサービス、Graph の代役に対して呼び出し、誰の人でどのマシンか、2 つの経路の順序、各上流に
要求するときのトークン、拒否、そしてツールのフォルダーが保持するスキーマを確かめます。`cargo test` がこれらを
すべて実行します。コンソールプラグインのバンドルは、ブラウザーテストを `client/tests/` に持ちます。画面はそこに
ある小さな Nuxt ホストの中で単独で動き、クライアントの開発サーバーが配信し、画面が変更した内容を保持する
サービスの代役を相手に、Chromium 上でマウス操作されます。`tests/browser/mail-drag.test.ts` は一覧の行をメール
ナビのフォルダーとラベルへ、フィルタールールを別の場所へ移し、ページを再読み込みしてそれぞれの結果を読み
取ります。`tests/browser/mail-kind-actions.test.ts` は、メールを移動しない種類のアカウントで、広い画面、
狭い画面、スマートフォンの幅のいずれでも移動の操作が表示されないことを確かめます。`tests/browser/mail-servers.test.ts` は、
広い画面とスマートフォンの幅で、接続テストとともに自分のサーバーを保存し、新しいサーバーを含めて選んだサーバーでアカウントを追加します。バンドルのチェックは型チェックの後にこれらを実行します。その他の振る舞いテストは先送りされています。
最小限のサービスが新しいリポジトリ上で動くようになった時点でここで書いて実行し、旧来の振る舞いが何を守って
いたかは `docs/inventory.md` が一覧にしています。ビルドチェックは `cargo check --all-targets` とバンドルの型
チェックです。

## 構成

| フォルダー | 内容 |
|---|---|
| `src/` | サービス、クライアント、OpenAPI ドキュメント、MCP サーバーとそのコマンド。独自のモジュールに分かれた 1 つのクレートです |
| `examples/` | `docs/openapi.json` が保持するとおりに OpenAPI ドキュメントを出力する `openapi` と、ホスト型ツールのスキーマをそのフォルダーに書き出す `tool_schemas` |
| `migrations/` | ストア。テーブルはこれらの文を順に実行して作られます |
| `wording/` | サービス自身の文言。1 言語につき 1 ファイルです |
| `plugin/` | ハーネスプラグインのスキル `skills/bmo-mail/` |
| `tools/` | ホスト型ツール `sent-mail/`: マニフェスト、スキーマ、マニュアル |
| `client/` | コンソールプラグインのバンドル: メール画面。独立したプロジェクトです |
| `deploy/` | サービスのユーザーユニット |
| `docs/` | サービスが行うことについての正典となるドキュメントと、OpenAPI ドキュメント |
| `tests/` | 現在ある振る舞いテスト |

ルートには、Cargo マニフェスト、`LICENSE`、`testbed.toml`、`install.toml`、`rustfmt.toml`、`CLAUDE.md`、
`PERSONAL-DATA.md`、`korean-ledger.json`、`settings.toml`、そしてデプロイが与えるローカル設定の例である
`settings.local.toml.example` があります。

## コンソールプラグインのバンドル

`client/` は、bmo-ui 上のコンソールバンドルとしてメール画面を持ちます。このバンドルは bmo-chat のコンソールの面
(`docs/api.md`、「The console plugin bundle」)を通じて、bmo-ui のコンソールプラグイン契約(bmo-ui の
`docs/console-bundles.md`)を守ります。`bun run bundle` は bmo-ui のバンドルビルドで `client/console/` から
モジュール、スタイルシート、文言、そしてビルドの土台となったレイヤーをビルドし、サービスは宣言が作る
マニフェストの隣でそれらを配信します。bmo-chat が固定する bmo-ui リリースと bmo-text の TypeScript パッケージの
パックが、独自のインストール、型チェック、ビルドのために `client/vendor/` の下にあるので、クローンには他の
チェックアウトが要りません。ボディの型は `client/shared/openapi.ts` が定め、このファイルは `bun run openapi` が
`docs/openapi.json` から生成します。バンドルのチェックは `client/` の中で実行する `bun run check` で、固定された
インストール、型チェック、ブラウザーテストからなります。

## バージョン

バージョンはセット全体のもので、ビルド時に git タグから読み取り、ヘルス、MCP サーバー、`--version` が
このバージョンで応答します。クレートのバージョンは動かないプレースホルダーです。バージョンは bmo-chat の `docs/conventions.md`「Versions」が
定めるとおり、オーナーが宣言したリリースでのみ上がります。コミット、デプロイ、契約の変更ではバージョンは
上がらず、デプロイはコミットで区別します。
